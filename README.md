## Columns

Header: `algorithm,tuple_run_index,key_id,num_channels,thresshold_sum`

| column | type | range | meaning |
|---|---|---|---|
| `algorithm` | string | names from `hash_functions_arr` | `toeplitz`, `jhash`, `chaskey`, `halfsiphash`, `siphash`, `xorhash` |
| `tuple_run_index` | int | 1 … `floor(N_tuples / WINDOW_SIZE)` | window index within one run (one `key_id` × `num_channels`); `count / WINDOW_SIZE` |
| `key_id` | int \| `N/A` | `0 … NUM_KEYS-1` | index of the random key for a keyed hash; `N/A` if `algo.keyed == false` |
| `num_channels` | int | `{8, 16, 20, 32, 40, 64, 128}` | number of DMA channels (`CHANNEL_COUNTS`) |
| `thresshold_sum` | float | ≥ 0 | packets above the fair share in this window, **in per-mille (‰) of the window size** — see below |

One row = one window of one run at one channel count.
Row count = `N_algorithms × (keyed ? NUM_KEYS : 1) × |CHANNEL_COUNTS| × N_windows`.

## Constants (frozen)

| constant | value | note |
|---|---|---|
| `WINDOW_SIZE` | `150000` | packets per window |
| `NUM_KEYS` | `16` | random keys per keyed hash |
| `KEY_SEED` | `65536` | seed for the `std::mt19937` that generates the keys (deterministic) |
| `RSS_KEY_SIZE` | `64` | key length in bytes |
| `CHANNEL_COUNTS` | `{8, 16, 20, 32, 40, 64, 128}` | DMA channel counts under test |
| `TUPLE_SIZE` | `37` | bytes per tuple |

**Windows:** `N_windows = floor(N_tuples / WINDOW_SIZE)`. The last partial window is
dropped (a window is emitted only when `count % WINDOW_SIZE == 0`).
E.g. `data/output.csv` has ≈ 4,555,318 tuples → 30 windows.

**Windows are independent, not cumulative:** the histogram is zeroed after every
window (`std::fill(...)`), and also at the start of every run.

## `thresshold_sum` — exact definition

`computeOverThressholdSum(histogram, window_count, num_channels)`:

```
avg  = window_count / num_channels          // ideal even load per channel
sum  = Σ_i  max(0, histogram[i] - avg)       // overloaded channels only, amount above avg
thresshold_sum = sum / (WINDOW_SIZE / 1000)  // = sum / 150  → per-mille of the window size
```

`window_count` is always passed as `WINDOW_SIZE` (150000).

### Consequence for aggregation (important)

`thresshold_sum` is already **per-mille of a single window**. Therefore:

- the **mean** of `thresshold_sum` over the windows of one run
  = (packets above fair share for the whole run) / (packets in the run) × 1000
  = **per-mille of the total packet count of that run**  ✅
- the **sum** of `thresshold_sum` over windows = that × window count → **not** per-mille
  of the total; if you want a sum, divide by the window count.

`analyze.py` therefore aggregates over windows with the mean (`key_value = mean`), not the sum.

## Quirks and known inconsistencies

- **`symmetry` is not in the CSV.** `benchmark` takes `argv[3]` ∈ {0,1,2}
  (0 = no symmetrisation, 1 = XOR half-fold, 2 = sort half-fold), but the resulting
  CSV carries no trace of which mode was used. It is distinguished only by the file
  name (`FULL_RUNTIME_sym0_results.csv` …). *TODO: add a `symmetry` column.*

- **`xorhash` has `keyed = true`.** [`hash_register.cpp`](../src/wrappers/hash_register.cpp)
  marks it as keyed, so it gets 16 rows (`key_id` 0–15). `xorHashRssWrapper` does
  XOR the key in. When `num_channels` is a power of two, all keys produce an
  **identical** `thresshold_sum` (XOR by a constant = a fixed permutation of the
  channel indices → same bucket counts). When `num_channels` ∈ {20, 40} the results
  differ. This is not a data bug — it is a property of XOR-fold hashing.

- **`toeplitz` drops the protocol byte.** `toeplitzRssWrapper` reads 9 × 4 = 36 B
  (`TOEPLITZ_WORDS = 9`), so byte 36 (`protocol`) never enters Toeplitz. The other
  hashes receive the full 37 B.

- **Old CSVs may use a different schema.** The files in `results/PER_FIELD/` were
  generated by an older benchmark (columns `fairness,chi,min_max_diff`, a different
  algorithm set: `ascon`, `crc32c`, `spookyhash`, `nsgahash4`). They are not
  compatible with the current `analyze.py`.

## Golden CSV

Before any refactoring, save a reference output from the current code on a fixed
small input and a fixed seed (`KEY_SEED` is already fixed). After the refactor,
compare byte for byte:

```
./benchmark <small_dataset> results/_golden/<name>.csv 0
# ... refactor ...
diff <(./benchmark <small_dataset> /tmp/new.csv 0; cat /tmp/new.csv) results/_golden/<name>.csv
```

Across "code move only" phases the `diff` must be empty. A phase that deliberately
changes the numbers (fixing a metric definition) must document it.
